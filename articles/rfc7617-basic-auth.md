# はじめに
認証方式の基礎となるRFC7617: Basic認証について調べたのでまとめます。」
RFC7617は前回紹介した[RFC7235](https://zenn.dev/keyem4251/articles/rfc7236-authentication-flamework)の上で動作をする具体的な認証の方式となります。
基本的に現在だとサービス間の認証として使われることは少ないですが、これ以降の認証方式へ変化していくうえでのもとになる仕組みとなっています。
またBasic認証と一緒にDigest認証についても説明します。

# 概要
Basic認証ではBase64を用いてエンコードされたユーザー名、パスワードのペアをBasicという文字列と合わせて送信することで認証を行う方式です。
RFC7235で定義されたチャレンジ&レスポンス方式の流れで、サーバーから `WWW-Authenticate: Basic realm="myapp" という形式でrealm（どこに対しての認証か？）とBasic認証で認証情報を送ってくださいというチャレンジがあります。
これに対して、クライアントは `Authorization: Basic QWxhZGRpbjpvcGVuIHNlc2FtZQ==` をHeaderに付与してレスポンスを返します。

# 詳細な設定
## charsetパラメータ
サーバーは `WWW-Authenticate: Basic realm="foo", charset="UTF-8"` という形式でどの文字コードでエンコードするかを具体的にすることができます。ただし現状ではUTF-8のみサポートしているという形になっています。
またユーザー名には「:」を入れることはできないという仕様になっています。これはユーザー名とパスワードをコロンで繋いでBase64エンコードするためです。

## 認証情報の再利用
認証が一度成功した場合に同様の認証情報を送ることでサーバーに認証をすることができます。
具体的には `http://example.com/docs/index.html` というURLに対してチャレンジ&レスポンス方式で認証をした場合にはクライアントは以下のURLにも同じ認証情報を付与して認証することができます。
すでに認証したパスの1つ上の部分（docsまで）
```
http://example.com/docs/
http://example.com/docs/test.doc
http://example.com/docs/?page=1
```
一方、以下にはチャレンジ＆レスポンスの形式を経ずに同じ認証情報を付与して認証することはできません。
```
http://example.com/other/
https://example.com/docs/
```

# Digest認証
RFCとしてはBasic認証とは別でRFC7616で定義されています。Basic認証と異なる点としてはサーバーからのチャレンジの際に `nonce="7ypS/xljBQA=6c2231d8..."` 、`algorithm=SHA-256` を付与します。
クライアントはサーバーから指定されたアルゴリズムにnonceを組み合わせて、ユーザー名、パスワードの値をハッシュ値に変換してサーバーに送信を行います。
HTTPの環境ではBasic認証よりも盗聴されてもパスワードは漏洩しないため安全という部分はあります。ただし通信内容全体の改ざんは防ぐことができません。

# まとめと所感
Basic認証に加えて簡単にDigest認証も調べました。Basic認証については現代ではHTTPSでの接続が当たり前となり社内の開発環境、ステージング環境などで手軽に保護をかけたい場合に利用されることがあるイメージです。
Digest認証についてはHTTP環境ではBasic認証よりも安全性が高かったですが、HTTPSが普及したこと、また通信内容全体の改ざんを防ぐことができないため最近では使われることはあまりなくなっています。
これらの技術の課題としては他にはユーザー名/パスワードをすべてのサーバーが保持する必要があること、認証/認可が分離されておらず認証が通るとクライアントが該当のURLに対して色々できてしまうことなどが挙げられます。
こういった課題を解決していくために現在ではIdPへの認証情報の集約、OIDC、OAuthによる認証/認可の分離などが行われて、認可についてはOAuth2.0によりBearerトークンを利用した手法などが使われています。
