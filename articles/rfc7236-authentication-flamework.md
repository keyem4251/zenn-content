# はじめに
認証認可に関連するRFCの基本となるRFC7235について調べたのでまとめます。
RFC7235はHTTP/1.1における共通の認証フレームワーク（認証をどういう流れで行うか）について定義しています。
具体的な認証方式（Basic認証、Digest認証、Bearer認証）によらないクライアント、サーバー間のやりとりの流れについて説明されています。
現在はRFC9110によりHTTP/1.1だけでなく、2、3とHTTPのバージョンによらない認証のフレームワークとなるように定義されています。（RFC9110は認証だけでなくHTTPの共通ルールが定義されています）
ただ認証についての基本的な概念を理解するうえでは軽量なRFC7235を抑えておけるとその後の認証系のRFCがわかりやすくなります。

# 概要
クライアントとサーバーでのやり取りをチャレンジ・レスポンス方式というものを使って認証しようと定義した。
チャレンジ・レスポンス方式とは
1. クライアントがサーバーにアクセスしてデータを取得しようとする
2. 認証資格が足りてない（最初にアクセスしたときなど）場合にサーバーがクライアントに `401 Unauthorized` を返す。この際にヘッダーでクライアントにどの認証情報が足りてないかを教える。→ この2がチャレンジ（課題の提示）
3. クライアントはサーバーからのレスポンスヘッダーを見て、認証情報を作成し、ヘッダーにつけてサーバーに再リクエストする。→ この3がレスポンス（資格情報の提示）
3の段階でBasic認証の場合には例えば、ユーザーがブラウザからユーザー名/パスワードを入力するというような流れになっています。

# チャレンジ/レスポンスの流れの詳細
## チャレンジ（サーバーがクライアントにレスポンスする）
`401 Unauthorized` のステータスコードでヘッダーに `WWW-Authenticate`という名前をつけて`realm=myapp`などのように文字列をつけてレスポンスします。realmとはサーバー側でどの範囲が同じ認証情報が必要かというのが分けられているものになります。抽象的で分かりづらい表現ですが、要は同じ認証情報（ユーザー名とパスワード）が必要な場合は同じrealmということになります。
Basic認証だと以下のようなイメージです。
```
WWW-Authenticate: Basic realm="myapp"
```
ブラウザはこれによりmyappの認証情報が必要なんだなということがわかり、ユーザーにmyappの認証情報の入力を促します。

## レスポンス（クライアントがサーバーに再リクエストする）
クライアントは `Authorization` にチャレンジで要求された認証情報を付与してリクエストを行います。例えば ユーザー名が `myapp-user`、パスワードが `myapp-pass` の場合にはそれらをやり取りする認証の方式（Basic認証、Digest認証、Bearer認証）の形式に変換して送ります。
先程のBasic認証だと以下のようなイメージです。ユーザー名、パスワードの間にコロンを付けて（`myapp-user:myapp-pass`）Base64エンコードする。
```
Authorization: Basic bXlhcHAtdXNlcjpteWFwcC1wYXNz
```
サーバーはこのBasic以降の内容を検証します。
この際にサーバー側で検証した結果、アクセスするのに十分な認証情報が出ないとなった場合には `403 Forbidden` を返します。

# まとめと所感
RFC7235自体はシンプルなクライアント、サーバー間のやり取りを定義しているだけですが、複数の認証方式がこの上で行われる土台となっています。ただ歴史的な経緯などによりチャレンジではAuthenticate（認証）と返すのにレスポンスではAuthorization（認可）とリクエストするあたりは昔は認証と認可があまり意識されていなかったということで、今見るとややこしい部分もあるなと思います。
