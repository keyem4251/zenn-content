# はじめに
HTTP上でBearerトークンを利用することで、OAuth2.0で保護されたリソースにアクセスする方法が記載されているRFC6750について調べたのでまとめます。
以前に認証認可のベースになる[認証フレームワークについて](https://zenn.dev/keyem4251/articles/rfc7235-authentication-flamework)、そこから認証の基本になる[Basic認証について](https://zenn.dev/keyem4251/articles/rfc7617-basic-auth)をまとめました。
認証・認可のベースになる認証フレームワークの上で、Basic認証では認証・認可が分離されていませんでした。そこから認証・認可が分離され、認可の部分だけを定義していくRFCであるRFC6750をまとめていきたいと思います。
具体的なOAuth2.0のフロー自体というよりはこの記事ではRFC6750についてに焦点をあてていきます。

# 概要
OAuth2.0のRFC6749ではアクセスしたいリソースオーナーの資格情報（認証情報）を直接使用するのではなく、一時的なアクセストークンをやり取りすることで、クライアントがリソースオーナーの情報にアクセスできるようにします。
ここでいうリソースとはアクセスする人のデータなどのことで、例えばGmailのその人が受信しているメールなどです。
このリソースにアクセスする際のアクセストークンにはBearerトークンという形式を利用します。
Bearerトークンとはそのトークンを持っているかどうかだけを検証し、実際にアクセスされるAPIやリソースへの人ごとの認証情報を持たない文字列になります。
実際のOAuth2.0ではアクセストークンが認可サーバーから払い出されるまでの流れもいくつかありますが、このRFCではクライアントはアクセストークンをリソースサーバー（上の例で言うとGmailのメールを返すAPI）へのリクエスト、リソースサーバーのトークン検証、クライアントへのレスポンスの流れが解説されています。またこの流れの中で利用されるアクセストークンの仕様についても記載されています。

# クライアントからの認可リクエスト
この時点ではアクセストークンはすでに認可サーバーからは払い出されている前提となります。ここまでのフローはRFC6749を参照してください。
クライアントがリソースサーバーにリクエストをする際には以下のようなリクエストを送ります。
```
GET /resource HTTP/1.1
Host: server.example.com
Authorization: Bearer mF_9.B5f-4.1JqM
```
AuthorizationヘッダーにBearer文字列のあとに実際のアクセストークン（`mF_9.B5f-4.1JqM`）を付与します。
Bearerトークンを受け付ける方法はいくつかありますが、例のAuthorizationヘッダーの方式が推奨されています。
その他には`access_token`に入れてフォームで送信する`x-www-form-urlencoded`形式、URLに`access_token`と直接アクセストークンを入れたURLクエリパラメータ形式の方法があります。URLクエリパラメータでのアクセストークンの受け渡しはURL自体がログに記録されたり、ブラウザの履歴に残るなどセキュリティリスクが高いため非推奨となっています。

# リソースサーバーからのレスポンス
リソースサーバーは認可リクエストを受け取り、トークンを検証します。検証した結果アクセストークンが正当なものであればリクエストされた内容を返します。Gmailであればログインしているユーザーのメールなど。
検証した結果不正なトークンとなる場合には以下のパターンでレスポンスを返してクライアントにステータスコードとともに `WWW-Authenticate` を付与してレスポンスします。
また`error`、`error_description`を付与して詳細情報を加えることもできます。
例えば以下はアクセストークンの期限が切れて、無効なトークンでリクエストした場合のレスポンスとなります。
```
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="example",
                  error="invalid_token",
                  error_description="The access token expired"
```
リソースサーバーはアクセストークンの検証の際に問題がある場合には以下のレスポンスを返します。（RFCではSHOULDとなっているので実装していないリソースサーバーもありえる）
- リクエストに必須パラメータが足りてない場合には `400 (Bad Request) `
- アクセストークンが期限切れ、署名が不正、無効化されているな場合には `401 (Unauthorized) `
  - クライアントは認可サーバーにリクエストしなおして、アクセストークンを取得し直すことで対応
- アクセストークンに含まれている権限では足りないリソースにアクセスしている場合には `403 (Forbidden)`
  - 403の場合にはレスポンスに `scope` パラメータを含めて必要な権限をリソースサーバーがクライアントに伝え直して、クライアントはそのアクセストークンを取得し直すことで対応

# Bearerトークンのセキュリティ上の注意事項
Bearerトークンはそのトークンを持っている人はだれでもリソースにアクセスできてしまします。Gmailを例に取るとこれはトークンが漏洩すると、メールの所有者かどうかが検証されるわけではなく、メールが見れるということです。
そのためセキュリティ上、気をつける事項が色々あります。
- 攻撃者による偽のトークンの生成、有効なトークンの有効期限など中身の改ざん
- 通信経路やブラウザの履歴、ログなどからのトークンの漏洩
- 攻撃者がトークンを本来のリソースサーバーではなく、他のリソースサーバーへ利用して、他のリソースサーバーの検証が通ってしまう
- 過去に盗聴したトークンを攻撃者が再利用する
これらへの対策としては以下が挙げられています。
- デジタル署名などによるトークンの保護 → 偽のトークン、中身の改ざんへの対策
- TLSによる通信の保護 → 通信経路の盗聴への対策
- どのアクセストークンがどのリソースサーバーへのトークンなのかをaudienceで利用範囲を明確にして、リソースサーバーでaudienceを検証する → アクセストークンと関係ないリソースサーバーでトークンが利用できることへの対策
- トークンの有効期限を短く設定し、スコープを抑える → 過去に盗聴したトークンの再利用する

全体的なセキュリティへのまとめとしては、TLSで署名を使ってトークンを保護する。そして、トークンのスコープ、有効期限、audience（どのリソースサーバーへのトークンか）をきちんと設定する。
またクエリパラメータには設定しない、Cookieにも平文ではトークンを設定せず、トークンを設定する場合にはCSRF対策を行うというものです。

# まとめと所感
アクセストークンの基本的なリクエスト、レスポンスの流れはRFC7235をベースにしており、Basic認証などとフロー自体は似ています。
Basic認証などから認証・認可が分離されたことによりアクセストークンを受け渡す方式として定義されています。
さらにやり取りするトークン自体のセキュリティ的な対策が色々とできるようになっています。
ここからトークン自体のセキュリティ対策を色々と行うためにJWTなどのRFCが定義されているという流れなのかなと思います。
